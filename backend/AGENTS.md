# 项目规则

## 规则优先级

- 始终遵守本项目根目录下的 `coding-style.md`。
- `coding-style.md` 属于强制规则，不是建议项；生成、修改、补全 Java 代码时必须逐条执行。
- 用户本次明确提出的要求优先于通用规则；未明确的部分按照 `coding-style.md` 执行。
- 补充 JavaDoc、整理代码格式不视为无关重构。
- 除补充注释和格式整理外，不要擅自改变原有业务逻辑、方法签名、返回值、调用链或类结构。

## 回复要求

- 始终使用中文回复。
- 回答要直接，优先提供可复制、可执行的修改方案和完整代码。
- 不要只解释概念，能够给出代码时直接给出代码。
- 如果是报错问题，优先说明报错原因、出错位置和修改方式。
- 用户要求完整代码时，不得使用 `省略`、`...`、`其余代码不变` 等方式省略内容。

## Java 文件修改要求

- 只要新建或修改一个 Java 文件，就必须对该文件进行一次完整的 JavaDoc 检查，而不是只给本次新增的代码补注释。
- 必须补齐当前 Java 文件中所有缺失的类、接口、枚举、Record、内部类、字段、常量、构造方法和方法 JavaDoc。
- 普通类中的方法、Controller 接口方法、私有方法、静态方法、转换方法和工厂方法同样必须添加 JavaDoc，不能只给接口方法或实现类重写方法添加。
- 依赖注入字段，包括 `private final` 修饰的 Repository、Service、Client、Properties 等字段，也必须添加字段 JavaDoc。
- 已有注释不得删除；已有注释不完整时应在保留原意的基础上补充。
- 修改完成后，必须按照 `coding-style.md` 中的“提交前检查清单”逐项自检，确认没有遗漏后再输出代码。

## 代码修改边界

- 不要随意大范围重构，除非用户明确要求新建类、拆分类或重构。
- 修改代码时优先只处理当前问题相关逻辑。
- JavaDoc 补全、必要的换行和格式整理属于允许范围，不受“只改当前问题相关部分”的限制。
- 不确定业务含义时，使用基于类名、方法名、参数名和现有调用关系能够确定的保守描述，不得虚构业务规则。

## 数据访问与类结构要求

- 本项目数据访问层统一使用 MyBatis-Plus；新增或修改数据访问代码时，禁止引入 JPA、`JpaRepository`、`@Entity`、`@Table`、`@Column` 等 JPA 类型。
- MyBatis-Plus 实体类统一使用 `@Data`，禁止手写 Getter、Setter、`equals`、`hashCode` 和 `toString` 方法。
- Mapper 必须继承 `BaseMapper<T>`，并使用 `XxxMapper` 命名；业务层通过 Mapper 完成数据库读写。
- 禁止在类、接口、枚举或 Record 内声明内部类、静态内部类、内部接口、内部枚举和内部 Record。
- 请求对象、响应对象、异常对象、配置对象和转换对象必须拆分为独立的顶级 Java 文件；一个公开顶级类型对应一个 Java 文件。
